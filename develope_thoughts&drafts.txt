We’ll focus on q. q returns the number of tasks in the fixedPool, and these tasks are submitted in the start function of runtime.
In main, a handler is defined and bound to the runtime rt, and then executed

q returns len(p.tasks), and tasks is a channel. That means the maximum value returned here is exactly the queue size we configured in fixedPool
(because of this line: tasks: make(chan func(), max(0, queue)),)

So we observe an interesting phenomenon: on the left side, the max q is a bit over 1k, almost the 2048 defined in main,
but on the right side, q hits the task channel capacity limit of 256. As a result, q stays full (256) for three consecutive intervals.

That means during this period, a lot of data is actually being backlogged on the producer side — it can’t be consumed, and can’t even enter the waiting queue.

So when I implement load balancing later, this is exactly the kind of scenario I’ll need to address.
